# Atlas app architecture

Mazi combines the Atlas interface and the complete local archive engine in one app as of 14 October 2026. This supersedes the separate Atlas and numbered phase runtimes. D18 adds hosted PostgreSQL/private Storage to this runtime; public production deployment and milestone acceptance remain separate.

## Runtime

`npm run dev` supervises a Vite interface and a loopback Python API/worker. Vite forwards `/api`, `/health` and `/land.geojson` without rewriting the browser Host, preserving Origin validation. The browser uses one origin and one HttpOnly session cookie. `npm start` builds the interface and serves both assets and APIs from Python.

`python -m mazi` is the backend entry point. With ignored `.env.supabase` present, normal startup selects hosted PostgreSQL/private Storage; `--local` or `MAZI_BACKEND=local` retains SQLite and file keys in `.mazi-imports`. Hosted scratch defaults to `.mazi-hosted`; it is separate from the local source. The background worker uses a separate connection with the same configuration. Startup never transfers an archive or seeds samples. The historical `.mazi-pilot` archive remains separate. [Hosted setup](SUPABASE_SETUP.md) documents credentials, transfer and recovery.

## Ownership

| `src/features/` | Imports, review, places/sources, discovery, answers/evidence and advanced memories in the shared shell. |
| `mazi/persistence.py`, `mazi/storage.py` | Backend selection, compatible rows/binding, schema-scoped transaction locks, verified private bytes and deletion receipts. |

| `mazi/imports/`, `mazi/archive/` | Resumable ingestion, provenance, correction, duplicates and accepted memories. |
| `mazi/sources/`, `tools/apple-photos/` | Source intake, shared places, Discord and the macOS Photos companion. |
| `mazi/discovery/`, `mazi/answers/` | People, hiding, consent, search and evidence-based answers. |
| `mazi/memories/` | Recaps, stories, revisions, capsules, subevents, slideshows, video and notices. |
| `tests/backend/`, `tests/browser/`, `tests/unified.spec.ts` | Domain regression contracts, fixture servers and integrated app journeys. |

`src/useEntry.ts` owns loading, signed-out, onboarding, ready and connection-error states. `src/Entry.tsx` renders login and the reusable introduction. The entry gate precedes every route, including samples. Shared-mode inherited HTTP authorization requires a mapped profile and current configured-circle membership; other circle IDs and legacy entry endpoints are denied. The additive profile/policy tables preserve existing user UUIDs, ownership and credentials. Introduction completion persists per profile; browser sessions expire after 30 days.

React owns routes and feature lifecycles. Existing feature workflows are scoped DOM modules with imported HTML fragments. Each mount owns its requests, timers and object URLs and disposes them on navigation or backgrounding. They are bundled application modules, without standalone pages, script injection or iframes. The migrated imperative modules remain JavaScript; the shared lifecycle, registry and Atlas code are TypeScript. Converting individual forms to React can happen within these feature boundaries.

## Atlas data and appearance

The interface uses self-hosted Instrument Serif, Geist and Geist Mono with the Luminous night night/day tokens under [D18](DECISIONS.md#luminous-night-visual-world-14-october-2026); the theme preference is the only value kept in localStorage (`mazi.theme`). Atlas keeps the procedural Fiber/Three chart until the globe stage replaces it. The chart displays at most three current memory planes. It is a chronological visual index, not inferred geography. Private textures are owned and disposed by the mounted scene. Keyboard/touch HTML controls and flat-view recovery remain available.

The server builds cards from authorized photographs and fully visible approved events. Cross-year and undated records remain available with honest date labels. It never borrows fictional messages or dates. A hidden or partially inaccessible event cannot expose its title through Atlas. The explicit `?demo=1` sample uses checked-in synthetic fixtures; a new personal archive stays empty.

## Local scope

Imports support the existing synthetic archive formats and JPEG/PNG validation. People use manual associations and confirmed identities. Related search has an offline baseline and optional local CLIP model. Answers are extractive and preserve abstention, consent and live evidence checks. Capsules use server UTC unlock. Video remains a silent, bounded MJPEG AVI download. Notifications remain opt-in and in-app.

Words & filters search supports circles above 1,000 visible photographs with exact totals and stable ID pagination. The larger-circle route scans authorized origin metadata in 256-row keyset pages, retains complete evidence for one photograph, and hydrates People only for the returned page. It preserves Unicode case-folded matching, filters, corrections, personal visibility and derivative cleanup. Circles at or below 1,000 retain the existing keyword path, including valid large imported metadata. No schema change or full-text index is required.

The larger-circle keyword route has explicit UTF-8 payload ceilings: 64 KiB per origin, 8 MiB per photograph and 64 MiB per request. SQL rejects an oversized origin before returning its payload. The per-photograph and per-request ceilings count consumed payload; a 256-row page can prefetch up to 16 MiB of payload before exhaustion is detected. These are not network-transfer or process-memory caps. A cooperative two-second scan budget is checked between pages; it is not a hard timeout, cannot interrupt a single SQL query or JSON parse, and excludes the initial visibility probe and final People hydration. Exhaustion returns HTTP 400 with `code: "capacity_exceeded"`, without partial results or counts. SQLite uses byte lengths; the PostgreSQL branch uses `octet_length`, but hosted query plans, driver memory and runtime timing remain unverified. Synthetic local endpoint measurements do not establish whole-page startup performance: discovery state still builds archive-wide People and the interface still loads Atlas.

A direct answer citation loads only its requested photograph and rechecks current group membership, personal visibility, live origins, processing consent and annotation-author eligibility. It remains available above 1,000 photographs without scanning unrelated answer records. Answer generation retains three complete live-evidence snapshot checks.

Memory answers use the existing route for requests initially at or below 1,000 visible photographs. Larger requests stream complete authorized evidence at each of the three checks, preserving the exact evidence fingerprint, matching totals, date uncertainty and at most five citations. The route stays fixed through delivery. Larger requests allow 64 KiB of raw JSON per live origin, 68 KiB of projected text per row, 8 MiB and 8,192 origins per photograph, and 64 MiB and 100,000 origins per check. Each eligible evidence record is limited to 64 KiB serialized JSON. A 128-row page can prefetch up to 8.5 MiB; three checks can consume up to 192 MiB. These are processing ceilings, not process-memory limits. Synthetic local stress fixtures reached about 90 MiB process RSS for multibyte metadata and 67 MiB for distinct words; those observations are not maxima or evidence of hosted suitability. Cooperative checks allow three seconds per check and eight seconds per answer, including initial routing and delivery; they cannot interrupt a database lock, SQL query or JSON operation. Exhaustion returns a typed capacity error without partial answers. A failed initial check rolls back usage; failures after the initial transaction retain the counted request without adding processing seconds. Questions stay available for explicit retry. Direct citation loading is unchanged.

Related search, local indexing and duplicate/event suggestions retain a 1,000-visible-photograph limit per circle. Filters do not reduce the set checked by those guards. Capacity failures use the typed HTTP response above; other invalid requests retain generic validation errors. Search preserves its query and filters and offers an explicit Words & filters action after a related-search capacity failure. Review keeps prior decisions accessible and distinguishes unavailable suggestions from an empty queue. Gallery and timeline pagination remain available beyond 1,000 photographs. Larger-archive browser and hosted-runtime acceptance remain separate from local backend and DOM checks.

Local synthetic SQLite measurements on 2026-10-19 used 10,000 photographs, 20,000 origins, 20 People and two tags per photograph. Five interleaved first/final-page runs took median 0.37–0.38 seconds with 768-character contexts and 0.65–0.66 seconds with 2,000-character contexts, issuing 87 SQL statements. Separate traced peaks were 0.67 MiB and 1.00 MiB. A fresh-process dense-JSON probe combining a 16 MiB raw page with an 8 MiB photograph reached about 150 MiB process RSS from a 25 MiB baseline; a separate 8,192-origin photograph reached about 145 MiB. These fixtures establish bounded local behavior, not hosted throughput or whole-application memory guarantees. Traced runs disabled only the cooperative clock to separate instrumentation overhead; timing and RSS results above used the production budget.

D18 synthetic checks establish hosted database/private-byte behavior for this application, including restart and recovery. They do not establish public production deployment, representative exporter compatibility, physical-device performance or production milestone acceptance. The Free project cannot promise the planned 20 GiB allocation; arbitrary orphan collection remains deferred. See [the consolidation evidence](../work/poteto/unified-app/VERIFICATION.md) and [README](../README.md) for commands.

Shared Places retains a 1,000-location map limit, counted across authorized live origins before filters. Map failure no longer blocks source connections or owned-contribution recovery. Archive export independently scans complete locations for its captured visible photograph set in 128-row keyset pages and writes UTF-8 JSON incrementally into the ZIP. Each projected record is bounded before transfer and has a 2 KiB serialized limit. During ZIP construction, only the bounded location scan holds the existing writer lock to stabilize mutable location dates. That construction scan’s cooperative three-second budget includes elapsed lock-wait time, but cannot interrupt lock acquisition, a database query or a JSON operation. The final 128 MiB archive limit includes ZIP structure and all appended metadata. Export still materializes the archive and other metadata, retains a 1,000-photograph limit, and does not provide a whole-export atomic snapshot. These local safeguards do not establish hosted memory or browser acceptance.

Archive download admission fingerprints the exact serialized metadata plus internal source and object identities while building, then compares a current metadata-only projection under the existing writer transaction. A changed visible set is rejected before the metadata rescan. Policy/content changes return a pre-header conflict, lost membership retains denial, and lock contention remains retryable. The final check adds metadata queries and writer-lock hold time, but no second original/resource downloads. No new global validation deadline or smaller imported-metadata ceiling is introduced in this correctness repair; existing location and lock budgets remain. The final validation also holds the writer transaction; its location subscan retains a three-second scan budget without imposing a whole-validation deadline. Count expansion and disk-backed delivery are separate work.

Synthetic local final-validation measurements used five untraced samples per fixture and separate traced runs. A 1,000-photo fixture had a median 136 ms writer transaction and 7,034 SQL statements; 20 People with 20,000 tags took about 916 ms and 167,054 statements. A 5,001-origin photograph took about 565 ms, and a legal 5.48 MB Messenger origin about 453 ms. Separately traced peaks ranged from about 5.19 MB to 38.97 MB. Every final validation performed zero original/resource reads. These observations disclose added lock and allocation costs; they are not maxima, hosted performance evidence or a count-expansion justification.
