# Atlas app architecture

Mazi combines the Atlas interface and the complete local archive engine in one app as of 14 October 2026. This supersedes the separate Atlas and numbered phase runtimes. D18 adds hosted PostgreSQL/private Storage to this runtime; public production deployment and milestone acceptance remain separate.

## Runtime

`npm run dev` supervises a Vite interface and a loopback Python API/worker. Vite forwards `/api`, `/health` and `/land.geojson` without rewriting the browser Host, preserving Origin validation. The browser uses one origin and one HttpOnly session cookie. `npm start` builds the interface and serves both assets and APIs from Python.

`python -m mazi` is the backend entry point. With ignored `.env.supabase` present, normal startup selects hosted PostgreSQL/private Storage; `--local` or `MAZI_BACKEND=local` retains SQLite and file keys in `.mazi-imports`. Hosted scratch defaults to `.mazi-hosted`; it is separate from the local source. The background worker uses a separate connection with the same configuration. Startup never transfers an archive or seeds samples. The historical `.mazi-pilot` archive remains separate. [Hosted setup](SUPABASE_SETUP.md) documents credentials, transfer and recovery. On Vercel, `api/index.py` serves the same handler as one function and signed-in tabs drive the worker through `/api/work`; [deployment](DEPLOYMENT.md) describes the tradeoff.

## Ownership

| Directory | Responsibility |
| --- | --- |
| `src/App.tsx`, `src/Atlas.tsx` | Shared navigation, Atlas selection, memory detail, timeline and renderer recovery. |
| `src/useArchive.ts`, `mazi/atlas.py` | Live authorized Atlas cards, consistent projection, request cancellation and private-state invalidation. |
| `src/features/` | Imports, review, places/sources, discovery, answers/evidence and advanced memories in the shared shell. |
| `mazi/persistence.py`, `mazi/storage.py` | Backend selection, compatible rows/binding, schema-scoped transaction locks, verified private bytes and deletion receipts. |
| `mazi/identity/` | Shared profiles, transactional circle/code setup, sessions and retained legacy domain contracts. |
| `mazi/imports/`, `mazi/archive/` | Resumable ingestion, provenance, correction, duplicates and accepted memories. |
| `mazi/sources/`, `tools/apple-photos/` | Source intake, shared places, Discord and the macOS Photos companion. |
| `mazi/discovery/`, `mazi/answers/` | People, hiding, consent, search and evidence-based answers. |
| `mazi/memories/` | Recaps, stories, revisions, capsules, subevents, slideshows, video and notices. |
| `tests/backend/`, `tests/browser/`, `tests/unified.spec.ts` | Domain regression contracts, fixture servers and integrated app journeys. |

`src/useEntry.ts` owns loading, signed-out, onboarding, ready and connection-error states. `src/Entry.tsx` renders login and the reusable introduction. The entry gate precedes every route, including samples. Shared-mode inherited HTTP authorization requires a mapped profile and current configured-circle membership; other circle IDs and legacy entry endpoints are denied. The additive profile/policy tables preserve existing user UUIDs, ownership and credentials. Introduction completion persists per profile; browser sessions expire after 30 days.

React owns routes and feature lifecycles. Existing feature workflows are scoped DOM modules with imported HTML fragments. Each mount owns its requests, timers and object URLs and disposes them on navigation. Imports and Circle retain their mounted state and transfers when hidden; other feature routes dispose on backgrounding. The session gate preserves a ready import route during foreground session validation. Denied access, session changes and page closure still clear it. They are bundled application modules, without standalone pages, script injection or iframes. The migrated imperative modules remain JavaScript; the shared lifecycle, registry and Atlas code are TypeScript. Converting individual forms to React can happen within these feature boundaries.

## Atlas data and appearance

The interface uses self-hosted Instrument Serif, Geist and Geist Mono with the Luminous night night/day tokens under [D18](DECISIONS.md#luminous-night-visual-world-14-october-2026); the theme preference is the only value kept in localStorage (`mazi.theme`). Atlas keeps the procedural Fiber/Three chart until the globe stage replaces it. The chart displays at most three current memory planes. It is a chronological visual index, not inferred geography. Private textures are owned and disposed by the mounted scene. Keyboard/touch HTML controls and flat-view recovery remain available.

The server builds cards from authorized photographs and fully visible approved events. Cross-year and undated records remain available with honest date labels. It never borrows fictional messages or dates. A hidden or partially inaccessible event cannot expose its title through Atlas. The explicit `?demo=1` sample uses checked-in synthetic fixtures; a new personal archive stays empty.

## Local scope

Imports support the existing synthetic archive formats and JPEG/PNG validation. People use manual associations and confirmed identities. Related search has an offline baseline and optional local CLIP model. Answers are extractive and preserve abstention, consent and live evidence checks. Capsules use server UTC unlock. Video remains a silent, bounded MJPEG AVI download. Notifications remain opt-in and in-app.

Words & filters search supports circles above 1,000 visible photographs with exact totals and stable ID pagination. The larger-circle route scans authorized origin metadata in 256-row keyset pages, retains complete evidence for one photograph, and hydrates People only for the returned page. It preserves Unicode case-folded matching, filters, corrections, personal visibility and derivative cleanup. Circles at or below 1,000 retain the existing keyword path, including valid large imported metadata. No schema change or full-text index is required.

The larger-circle keyword route has explicit UTF-8 payload ceilings: 64 KiB per origin, 8 MiB per photograph and 64 MiB per request. SQL rejects an oversized origin before returning its payload. The per-photograph and per-request ceilings count consumed payload; a 256-row page can prefetch up to 16 MiB of payload before exhaustion is detected. These are not network-transfer or process-memory caps. A cooperative two-second scan budget is checked between pages; it is not a hard timeout, cannot interrupt a single SQL query or JSON parse, and excludes the initial visibility probe and final People hydration. Exhaustion returns HTTP 400 with `code: "capacity_exceeded"`, without partial results or counts. SQLite uses byte lengths; the PostgreSQL branch uses `octet_length`, but hosted query plans, driver memory and runtime timing remain unverified. Synthetic local endpoint measurements do not establish whole-page startup performance: discovery state still builds archive-wide People and the interface still loads Atlas.

A direct answer citation loads only its requested photograph and rechecks current group membership, personal visibility, live origins, processing consent and annotation-author eligibility. It remains available above 1,000 photographs without scanning unrelated answer records. Answer generation retains three complete live-evidence snapshot checks.

Memory answers use the existing route for requests initially at or below 1,000 visible photographs. Larger requests stream complete authorized evidence at each of the three checks, preserving the exact evidence fingerprint, matching totals, date uncertainty and at most five citations. The route stays fixed through delivery. Larger requests allow 64 KiB of raw JSON per live origin, 68 KiB of projected text per row, 8 MiB and 8,192 origins per photograph, and 64 MiB and 100,000 origins per check. Each eligible evidence record is limited to 64 KiB serialized JSON. A 128-row page can prefetch up to 8.5 MiB; three checks can consume up to 192 MiB. These are processing ceilings, not process-memory limits. Synthetic local stress fixtures reached about 90 MiB process RSS for multibyte metadata and 67 MiB for distinct words; those observations are not maxima or evidence of hosted suitability. Cooperative checks allow three seconds per check and eight seconds per answer, including initial routing and delivery; they cannot interrupt a database lock, SQL query or JSON operation. Exhaustion returns a typed capacity error without partial answers. A failed initial check rolls back usage; failures after the initial transaction retain the counted request without adding processing seconds. Questions stay available for explicit retry. Direct citation loading is unchanged.

Related search, local indexing and duplicate/event suggestions support up to 10,000 visible photographs per circle within explicit local processing budgets. Larger related searches stream complete authorized metadata in 256-origin pages and rank at most 10,000 compact result rows, hydrating People only for the returned page. Both baseline and learned encoders use only current cached vectors above 1,000 photographs; explicit index batches compute at most five photographs outside the writer transaction and retain the consent-generation and evidence-fingerprint rechecks. Missing vectors remain explicit in the unindexed count. Smaller circles retain their established lazy baseline indexing and large-origin compatibility. Each larger metadata scan allows 64 KiB per origin, 8 MiB and 8,192 origins per photograph, and 64 MiB and 100,000 origins per request, with a cooperative 15-second scan budget. Index batches scan before inference and again for the complete remaining count. Larger event suggestions resolve every live origin before grouping, with 64 KiB per origin, 64 MiB total metadata and 15 seconds of cooperative processing. Larger duplicate review computes compact preview signatures, then uses seven disjoint hash blocks to retain every candidate within six differing bits. It preserves pair ordering and decisions, with 256 MiB of preview input, five million candidate comparisons and 15 seconds of cooperative processing. Dense or large-preview archives can exhaust those budgets without a partial suggestion response. Review holds the local writer transaction while deriving suggestions. These cooperative checks cannot interrupt lock acquisition, SQL queries, decoding or model inference. Filters do not reduce the visible set checked by the photograph caps. Capacity failures use the typed HTTP response above; other invalid requests retain generic validation errors. Search preserves its query and filters and offers an explicit Words & filters action after a related-search capacity failure. Review keeps prior decisions accessible and distinguishes unavailable suggestions from an empty queue. Gallery and timeline pagination remain available beyond 1,000 photographs. Larger-archive browser and hosted-runtime acceptance remain separate from local backend and DOM checks.

Local synthetic SQLite measurements on 2026-10-19 used 10,000 photographs, 20,000 origins, 20 People and two tags per photograph. Five interleaved first/final-page runs took median 0.37-0.38 seconds with 768-character contexts and 0.65-0.66 seconds with 2,000-character contexts, issuing 87 SQL statements. Separate traced peaks were 0.67 MiB and 1.00 MiB. A fresh-process dense-JSON probe combining a 16 MiB raw page with an 8 MiB photograph reached about 150 MiB process RSS from a 25 MiB baseline; a separate 8,192-origin photograph reached about 145 MiB. These fixtures establish bounded local behavior, not hosted throughput or whole-application memory guarantees. Traced runs disabled only the cooperative clock to separate instrumentation overhead; timing and RSS results above used the production budget.

D18 synthetic checks establish hosted database/private-byte behavior for this application, including restart and recovery. They do not establish public production deployment, representative exporter compatibility, physical-device performance or production milestone acceptance. The Free project cannot promise the planned 20 GiB allocation; arbitrary orphan collection remains deferred. See [the consolidation evidence](../work/poteto/unified-app/VERIFICATION.md) and [README](../README.md) for commands.

Shared Places supports 20,000 authorized live location records, with an 8 KiB stored-text record budget and an 8 MiB complete serialized point-list budget before filtering. It scans 128-row keyset pages under a stable projection transaction with a cooperative 15-second processing budget. Map failure no longer blocks source connections or owned-contribution recovery. Archive export independently scans complete locations for its captured visible photograph set in 128-row keyset pages and writes UTF-8 JSON incrementally into the ZIP. Each projected record is bounded before transfer and has a 2 KiB serialized limit. During ZIP construction, only the bounded location scan holds the existing writer lock to stabilize mutable location dates. That construction scan’s cooperative three-second budget includes elapsed lock-wait time, but cannot interrupt lock acquisition, a database query or a JSON operation. The final 128 MiB archive limit includes ZIP structure and all appended metadata. HTTP export builds one private completed file-backed ZIP for up to 10,000 visible photographs. Manifest origins, retained-resource metadata, People and personal metadata are serialized through private disk spools without retaining their complete graphs. Original identity scans read one origin at a time; compact People, event and city projections use 128-row keyset pages, while potentially large resource metadata uses one-row keyset pages. There is no whole-export atomic snapshot. These local safeguards do not establish hosted memory or browser acceptance.

Archive download admission fingerprints the exact serialized metadata plus internal source and object identities while building, then compares a current metadata-only projection under the existing writer transaction. A changed visible set is rejected before the metadata rescan. Policy/content changes return a pre-header conflict, lost membership retains denial, and lock contention remains retryable. The final check adds metadata queries and writer-lock hold time, but no second original/resource downloads. No new global validation deadline or smaller imported-metadata ceiling is introduced in this correctness repair; existing location and lock budgets remain. The final validation also holds the writer transaction; its location subscan retains a three-second scan budget without imposing a whole-validation deadline. The later metadata streaming and 10,000-photograph expansion preserve this admission boundary.

Synthetic local final-validation measurements used five untraced samples per fixture and separate traced runs. A 1,000-photo fixture had a median 136 ms writer transaction and 7,034 SQL statements; 20 People with 20,000 tags took about 916 ms and 167,054 statements. A 5,001-origin photograph took about 565 ms, and a legal 5.48 MB Messenger origin about 453 ms. Separately traced peaks ranged from about 5.19 MB to 38.97 MB. Every final validation performed zero original/resource reads. These observations disclose added lock and allocation costs; they are not maxima, hosted performance evidence or a count-expansion justification.

The HTTP archive route uses a context-owned anonymous temporary file from the first byte, one ZIP writer chain, and 256 KiB original/resource and response copies. It shares authorized object locators with existing byte APIs and preserves hosted materialization/checksum verification. A high-water byte guard counts payloads, metadata and ZIP structure without double-counting seek-back header updates. The artifact is exposed only after ZIP closure, final size validation and policy admission. Pre-header failures return JSON; failures after headers close the connection without appending another response. Temporary artifacts close on success and failure. The compatibility `export_archive` bytes API still materializes its returned ZIP; only file-based HTTP delivery avoids that allocation. Metadata now streams through private spools. Individual legal origin/resource records and scalar strings still materialize, as do one person's bounded asset/city sets, the bounded city cache, visible IDs and ZIP central-directory records. These remaining allocations prevent a universal constant-memory claim.

Historical measurements for the earlier completed-file delivery change used a fresh process and a 100,798,546-byte photo ZIP. They observed 622,113 traced bytes and 23,788 KiB process RSS for file construction, and 640,466 traced bytes / 23,872 KiB for file-based HTTP. The prior bytes path observed 126,080,150 traced bytes / 146,348 KiB. Five-run paired medians were 0.171 to 0.122 seconds for that fixture, 0.436 to 0.427 seconds for 1,000 small photos, and 0.618 to 0.626 seconds for dense People; SQL counts matched in those timed photo fixtures, and member hashes matched across all parity fixtures. Mixed retained-resource exports add four authorization-query statements through the shared locator. ZIP metadata writes use a fixed 256 KiB batching buffer without changing serialized values or fingerprint framing. Retained metadata can still dominate: the legal large-Messenger fixture observed about 39 MB traced allocations and 102,944 KiB RSS. These are measured local cases, not maximum memory or hosted capacity claims.

That earlier measured cloud runtime mounted its temporary directory on tmpfs. The anonymous export file occupied kernel-managed memory outside process RSS in that environment. The later metadata-streaming measurements were made locally on macOS; they do not establish the storage backing of a future hosted deployment. File-backed delivery reduces Python/process allocations but does not remove the payload from host memory or demonstrate physical-disk throughput; deployment storage must be assessed separately.

Export preflight uses the actual opened original file length against the ZIP writer's current high-water position before copying that original into the ZIP. Hosted materialization may already have downloaded and verified the object, so this is not a remote-transfer preflight. Stored asset size includes previews for storage-quota accounting and is not treated as exported payload size. Initial asset authorization, storage accounting and policy fingerprints remain unchanged. This early transfer check is only a lower bound; metadata, member headers and the central directory still count toward the final 128 MiB ZIP limit.

Export People projection reuses only each photograph's resolved city tuple within one projection call. Construction and final admission use separate fresh caches; the ordinary People endpoint keeps its existing repeated live checks. Retention is limited to 1,000 asset keys, 4,096 city entries and 262,144 Unicode characters. When a value does not fit, the projection recomputes it without caching; output is neither truncated nor refused. Full documents, source payloads and authorization results are not cached. The export city projection resolves one origin at a time without constructing search documents. Each person retains at most the supported photograph set and its resolved city set; associated memories stream individually. The JSON encoder still materializes one legal scalar value and the database driver still materializes one selected origin or resource record. This is a reduction in retained archive-wide metadata, not a constant-memory guarantee for arbitrary legal records. At most one metadata spool coexists with the completed-file ZIP, each bounded by the existing 128 MiB public metadata or ZIP allowance. Hosted object materialization can additionally require one private object file. Temporary storage capacity and backing filesystem require deployment-specific verification.

Fresh-process synthetic measurements compare the production city reuse with the prior implementation; timing and traced allocation include export plus ZIP-member hashing and content verification. For 1,000 photos, 20 People and 20,000 tags, SQL statements fell from 336,109 to 32,109 and median time from 2.088 to 0.614 seconds; all 1,005 ZIP member contents and order matched. A nonempty-city fixture reached the actual key and character retention limits with fresh caches in both passes: 1,000 keys, 2,000 city entries and 262,144 characters. Its SQL count fell from 296,137 to 30,137 and median time from 2.478 to 0.720 seconds, with identical output. A legal large-Messenger origin fell from 40 to two document builds and 3.417 to 1.303 seconds, but traced peak remained about 52.7 MB. These historical measurements precede the later metadata streaming change. Current record-size and hosted-runtime limits are described above.

Atlas reads live source origins through a nested streaming iterator inside its existing transaction, using the already authorized photograph set and unchanged live-owner join and insertion order. This avoids repeating asset/access/count queries for each photograph. Public origin readers, card construction, date resolution, event visibility and response order remain unchanged. No archive-wide source-message map or cross-request cache is retained; the response itself is still fully materialized.

Paired production checks using the frozen prior implementation return byte-identical HTTP responses. A legal 1,001-photo import drops from 6,035 to 3,032 SQL statements with the same 557,571-byte response; a 10,001-photo metadata fixture drops from 60,035 to 30,032. Overlapping events on 1,000 photos drop from 17,574 to 8,814 statements. Metadata-only stress fixtures with repeated 16 KiB source contexts, beyond the current chat adapter allowance, retain comparable traced Python peaks: grouped contexts about 1.15 to 1.14 MB, fully hidden contexts about 0.774 to 0.777 MB with the same empty response. Timing varies locally, so the acceptance result is query reduction with exact output/privacy and comparable allocation, not a general latency guarantee. Full-response size and hosted/browser performance remain separate limitations.

The production legal 10,000-photo import rerun also preserves all 10,000 cards and the exact 5,570,014-byte response while reducing HTTP SQL statements from 60,029 to 30,029; the candidate traced Python peak is about 30.55 MB. The retained synthetic fixture supports independent replay, without establishing hosted or physical-device acceptance.

## Import throughput and reporting

ZIP scans retain one archive and inventory iterator per worker between bounded 500-record checkpoints. Inventory rows commit in groups of at most 128 per SQL statement. A worker restart replays the committed prefix once. A competing checkpoint, cancellation, withdrawal, access removal, or failed transaction invalidates the retained scan. No new storage format or database migration is required.

The browser sends 512 KiB chunks under the existing upload limit. Transfer completion hashes the materialized file without loading an additional full archive into memory. Reports distinguish scanned records, media candidates, and records without media. Photo processing progress excludes records without media. Inventory still requires explicit confirmation before sharing. Terminal reports stop periodic polling; selecting a report fetches its latest state.

[Performance evidence](../work/poteto/import-performance/VERIFICATION.md) uses synthetic fixtures. Warm-worker reuse reduces repeat work, but serverless cold starts still replay the saved prefix. Initial materialization and parsing remain cooperative work that a batch limit cannot interrupt.
